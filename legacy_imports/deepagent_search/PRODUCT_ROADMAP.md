# 数据分析 Agent 产品定位与发展路线报告

生成日期：2026-07-07
依据：当前项目代码、`CODE_AUDIT_REPORT.md`、已验证运行结果。
边界：本报告只做产品定位、Demo 方案、MVP 路线和商业化判断，不重新做全面代码审计，不修改业务代码。

## 1. 当前项目定位

### 明确判断

当前项目本质上不是“通用数据分析 Agent”，也不是完整 BI 产品，而是一个面向制药经营数据的自然语言数据库分析 Agent Demo 原型。

它最适合发展成：

**制药行业库存与销售风险分析 Agent。**

更具体一点：它应该先服务制药企业、医药流通企业、区域销售团队、库存运营人员，帮助他们用自然语言分析药品库存、销量、销售额、区域表现和库存积压风险。

### 当前最有价值的能力

当前项目最有价值的能力不是 FastAPI，也不是 DeepAgents 框架本身，而是：

1. 已经有制药业务数据模型：`drugs`、`inventory`、`sales_records`。
2. 已经能把自然语言问题转成 MySQL 查询。
3. 已经能处理药品、库存、销售之间的多表关系。
4. 已经在 prompt 中写入关键业务口径，例如总库存、总销量、库存销量比、近 6 个月口径。
5. 已经有基础 eval，可以验证几个经营分析问题。

这说明项目已经有一个垂直业务分析雏形。它不应该转向泛泛的“上传任意文件然后问问题”，那会直接撞上 ChatGPT、Excel Copilot、Power BI Copilot 和大量数据分析 Agent。

### 最适合解决的问题

当前功能最适合解决这类问题：

- 哪些药品库存高但销量低？
- 哪些区域销售额最高或下滑明显？
- 哪些药品库存周转风险最高？
- 哪些产品销售额贡献最大？
- 某个药品当前库存是否合理？
- 经营周报中应该关注哪些异常？

这些问题有三个共同点：

1. 数据结构相对固定。
2. 业务口径可沉淀。
3. 分析结果能直接影响采购、销售、调拨、促销和补货决策。

### 通用 Agent 还是垂直 Agent

明确选择：**垂直行业数据分析 Agent。**

原因：

- 当前代码已经围绕制药数据建模，保留并扩展它成本最低。
- 通用数据分析 Agent 需要处理任意数据结构、任意行业语义、任意指标口径，当前项目承载不了。
- 垂直场景能把 prompt 中的行业规则沉淀成产品壁垒。
- 真实用户更愿意为“帮我发现库存积压和销售异常”付费，而不是为“我可以问数据库问题”付费。

### 制药数据场景应该保留、扩展还是替换

结论：**保留并扩展。**

不建议替换成通用电商、CRM、财务或 SaaS 指标 Demo。当前最有价值的部分就是制药库存和销售业务语义。应该把现有样例扩展为更完整的医药经营分析场景：

- 药品主数据；
- 批次和效期；
- 库存；
- 销售记录；
- 区域；
- 客户；
- 销售代表；
- 采购或补货记录；
- 近效期预警；
- 滞销和断货风险。

## 2. 推荐的唯一商业化方向

### 主方向

**制药行业库存与销售风险分析 Agent。**

产品一句话：

> 面向制药和医药流通企业的经营分析 Agent，自动发现库存积压、销量异常、区域销售变化和重点药品风险，并生成可追溯的经营分析报告。

### 为什么不是其他方向

| 方向 | 是否推荐 | 原因 |
|---|---|---|
| 通用数据分析 Agent | 不推荐 | 竞争最强，数据类型和业务语义太泛，当前代码复用价值低 |
| 企业经营分析 Agent | 不作为第一方向 | 太宽，行业口径难沉淀，获客话术不够尖锐 |
| 制药行业经营分析 Agent | 接近，但仍偏宽 | 可以作为长期方向，第一版应收窄到库存和销售风险 |
| 库存和销售分析 Agent | 接近，但行业不够明确 | 如果不限定制药，会变成泛零售/电商工具，竞争变强 |
| 中小企业老板自然语言 BI | 不推荐 | 老板不想配置数据库，也不关心 SQL，需求太分散 |
| 数据分析师 SQL Copilot | 不推荐 | 当前项目重点是业务分析，不是开发者工具 |
| 自动经营周报和月报 Agent | 可作为核心功能 | 更适合作为产品形态，不是行业定位 |
| 企业数据库问答 Agent | 不推荐 | 太泛，容易沦为“问数据库”，付费理由弱 |

### 商业化方向评分

评分 1-5，5 分最好。

| 标准 | 制药行业库存与销售风险分析 Agent | 判断 |
|---|---:|---|
| 与当前代码匹配程度 | 5 | 已有药品、库存、销售表和相关 prompt |
| MVP 开发难度 | 4 | 独立开发者可完成，先复用 MySQL + FastAPI + Agent |
| 用户痛点 | 4 | 库存积压、近效期、滞销、销售波动是真问题 |
| 用户付费意愿 | 4 | 如果能减少库存损失和提升销售管理效率，有付费基础 |
| 获客难度 | 3 | 需要找到医药流通/制药运营人员，但比泛企业 BI 更精准 |
| 竞争强度 | 3 | 会遇到 BI 和 ERP 报表，但垂直 Agent 差异更清楚 |
| 数据接入难度 | 3 | 第一版可从导出的 MySQL/CSV 开始，后续接 ERP |
| 商业扩展空间 | 4 | 可扩展到采购、效期、渠道、区域、销售代表绩效 |
| 产品壁垒 | 4 | 行业指标、异常规则、分析模板和 eval 数据集可沉淀 |

综合判断：这是当前项目投入产出比最高的方向。

## 3. 目标用户

第一批用户不要选“大型药企 CIO”或“所有数据分析师”。他们采购流程长、数据接入复杂、合规要求高。

第一批目标用户应是：

**中小型制药企业或医药流通公司的销售运营、库存运营、经营分析负责人。**

典型用户画像：

- 公司有药品、库存、销售、客户、区域数据；
- 数据通常在 MySQL、ERP 导出表、Excel 或财务/进销存系统中；
- 业务人员会 Excel，但不会稳定写 SQL；
- 老板或管理层经常要问“哪些货压着卖不动”“哪个区域突然变差”“这个月经营风险在哪里”；
- 现有 BI 看板只能看固定指标，临时问题仍要找数据同事。

## 4. 用户痛点

这些用户现在通常这样做分析：

1. 从 ERP 或进销存系统导出 Excel。
2. 手工透视表、筛选、VLOOKUP。
3. 找懂 SQL 的同事临时取数。
4. 把结果复制进周报或 PPT。
5. 老板追问口径时再返工。

主要麻烦：

- 临时问题多，固定 BI 看板覆盖不了。
- 药品库存、销量、效期、区域、客户之间经常要联表分析。
- 口径容易错，例如库存表和销售明细表直接 JOIN 后重复求和。
- 业务人员不懂 SQL，数据人员不懂业务细节。
- 报告周期固定，但异常出现不固定。
- 库存积压和近效期风险发现太晚。

## 5. 核心使用场景

第一版只做 5 个高频场景。

### 场景 1：库存积压风险分析

用户问：

> 找出库存销量比最高的药品，并说明哪些有积压风险。

系统输出：

- 药品名称；
- 总库存；
- 总销量；
- 库存销量比；
- 风险等级；
- 业务解释；
- 建议动作。

### 场景 2：近效期库存预警

用户问：

> 未来 90 天有哪些批次临近有效期？按风险排序。

系统输出：

- 药品；
- 批号；
- 仓库；
- 库存数量；
- 到期天数；
- 近期销量；
- 是否需要促销、调拨或停止补货。

当前代码没有近效期分析工具，但 `inventory.expiry_date` 已存在，扩展成本低。

### 场景 3：区域销售表现分析

用户问：

> 本期各区域销售额排名，哪些区域表现异常？

系统输出：

- 区域销售额；
- 销售占比；
- Top/Bottom 区域；
- 与历史周期对比；
- 可能原因和后续追问建议。

### 场景 4：重点药品经营分析

用户问：

> 分析连花清瘟的库存、销量、销售额和风险。

系统输出：

- 库存状态；
- 销售趋势；
- 区域分布；
- 客户贡献；
- 风险和建议。

### 场景 5：自动经营周报

用户点击：

> 生成本周经营风险周报。

系统自动输出：

- 本周销售概览；
- 库存风险；
- 近效期风险；
- 销售异常；
- 重点药品；
- 建议动作清单。

这是最适合收费的结果，不只是问答。

## 6. 完整 Demo 方案

### Demo 演示链路

推荐演示链路：

用户输入自然语言问题
→ Agent 识别这是库存/销售/区域/药品分析问题
→ 展示可用数据表和字段
→ 生成 SQL
→ 执行只读 SQL
→ 返回结构化数据表
→ 生成图表
→ 生成中文经营分析结论
→ 展示执行过程、SQL、数据依据和口径说明
→ 用户追问或一键生成报告。

### 当前已经具备的环节

| 环节 | 当前状态 | 代码依据 |
|---|---|---|
| Agent 编排 | 已有 | `agent/main_agent.py` |
| 数据库子 Agent | 已有 | `agent/sub_agents/db_sub_agent.py` |
| MySQL 查询 | 已有 | `tools/mysql_tools.py` |
| 自然语言生成 SQL | 已有 | DeepAgents + prompt |
| 制药业务 schema | 已有 | `sql/db.sql` |
| 经营分析 prompt | 已有 | `prompt/prompts.yaml` |
| 基础 eval | 已有 | `evals/db_agent_eval.py` |
| FastAPI 基础 | 已有 | `api/server.py` |

### 缺少的环节

| 缺失环节 | Demo 必要性 |
|---|---|
| API 调用 Agent | 必须，否则服务端 Demo 不闭环 |
| 简单前端或演示页面 | 必须，否则作品集说服力弱 |
| 执行过程展示 | 必须，用来体现 Agent 能力 |
| 结构化结果表格 | 必须，增强可信度 |
| 图表生成 | 建议必须，Demo 直观度大幅提升 |
| SQL 和口径展示 | 必须，避免“模型瞎说”的观感 |
| 固定演示问题按钮 | 必须，保证演示稳定 |
| 一键生成周报 | 强烈建议，这是产品化雏形 |

### Demo 最值得增加的 5 项功能

1. **把 `/api/task` 接到真实 Agent 调用。**
   最小实现即可：输入 query，返回 answer、thread_id、tool_steps。

2. **工具返回结构化结果。**
   不要只返回字符串。至少返回 SQL、columns、rows、row_count、error。

3. **增加一个极简 Web 页面。**
   一个输入框、几个示例问题按钮、结果表格、图表、SQL 展开区即可。不要做登录、租户、复杂布局。

4. **增加图表生成。**
   Demo 阶段用前端图表库或后端返回 chart spec。优先做柱状图、折线图、风险排行条形图。

5. **增加“经营风险周报”模板。**
   不是让用户随便问，而是一键输出库存风险、销售排行、区域异常、建议动作。

### 必须修复的技术问题

Demo 阶段不追求生产级，但这些必须修：

- `/api/task` 不执行 Agent；
- 空 query 也返回 started；
- eval 失败仍退出 0；
- Windows 控制台 emoji 编码导致 eval 假失败；
- 模型生成 SQL 没有最小只读保护；
- 第 5 个 eval SQL 没有按用户要求 `LIMIT 3`；
- 工具结果没有结构化，图表和表格无法稳定复用。

### Demo 阶段可以暂时不做的生产级功能

- 多租户；
- 完整 RBAC；
- 复杂权限模型；
- 私有化部署；
- 高并发任务队列；
- 复杂监控系统；
- 全量审计平台；
- 多数据库适配；
- 任意文件上传分析；
- 企业级 SSO。

Demo 的目标是让人看到一条完整、可信、稳定的分析链路，不是做成企业平台。

### 如何让 Demo 更有说服力

演示时不要只问“查询销售额最高的药品”。那像普通 SQL Copilot。

更有说服力的演示顺序：

1. 展示数据库里有药品、库存、销售三类数据。
2. 问一个容易出错的多表问题：总库存、总销量、库存销量比。
3. 展示 Agent 生成了先聚合再 JOIN 的 SQL，避免重复求和。
4. 展示结果表格和风险图。
5. 展示 Agent 给出业务建议，并明确口径。
6. 追问：“如果只看近 6 个月销量，风险会怎么变？”
7. 一键生成“库存风险周报”。

这能体现三件事：

- Agent 不是只聊天；
- 分析有数据依据；
- 业务口径有行业理解。

## 7. MVP 产品方案

### MVP 目标

让 3-10 个真实用户持续使用，而不是让很多人试一下。

第一版 MVP 应该验证：

1. 用户是否愿意把库存和销售数据接入；
2. 用户是否会反复使用库存/销售风险分析；
3. 用户是否愿意基于 Agent 输出做经营动作；
4. 用户是否愿意为自动周报、风险提醒、口径复用付费。

### 第一版必须有

| 功能 | 目的 |
|---|---|
| 连接一个 MySQL 或导入固定格式 CSV | 让真实用户能接入数据 |
| 数据表字段映射 | 把用户字段映射到药品、库存、销售标准模型 |
| 自然语言问数 | 保留 Agent 体验 |
| 库存风险分析模板 | 第一核心场景 |
| 区域销售分析模板 | 第二核心场景 |
| 重点药品分析模板 | 第三核心场景 |
| 自动周报/月报 | 形成持续使用理由 |
| 数据依据展示 | 表格、SQL、口径说明 |
| 分析规则可配置 | 阈值如库存销量比、近效期天数 |
| 基础 eval 和回归用例 | 保证演示和试用稳定 |

### 第二版再增加

| 功能 | 增加时机 |
|---|---|
| 多用户账号 | 有 3 个以上团队用户后 |
| 定时任务和消息推送 | 周报被真实使用后 |
| Excel 导出和 PDF 报告 | 用户开始转发报告后 |
| 异常趋势检测 | 有足够历史数据后 |
| 采购建议 | 库存和销售分析稳定后 |
| 销售代表绩效分析 | 用户明确需要管理销售团队时 |
| 企业微信/飞书推送 | 用户已有固定工作流后 |
| ERP/进销存系统连接器 | 有明确客户系统后 |

### 暂时不要做

- 通用文件聊天；
- 任意 Python 代码执行；
- 复杂图表编辑器；
- 拖拽式 BI 看板；
- 大而全的数据治理平台；
- 多模型路由；
- RAGFlow 知识库问答；
- Tavily 联网搜索；
- 多行业模板市场；
- 自动写入数据库或自动下采购单。

这些要么与当前项目无关，要么会扩大实现面，要么没有验证付费价值。

## 8. 第一版付费产品方案

### 1. 用户是谁

中小制药企业、医药流通公司、区域药品销售团队的经营分析负责人、销售运营负责人、库存运营负责人。

### 2. 用户接入什么数据

第一版只接三类数据：

- 药品主数据；
- 库存和批次数据；
- 销售记录。

先不要接财务、采购、CRM、生产、供应链全流程。

### 3. 用户进入产品后完成什么操作

1. 上传样例 CSV 或连接只读 MySQL。
2. 映射字段到标准模型。
3. 点击“生成库存风险分析”或“生成经营周报”。
4. 查看风险药品、SQL 数据依据、图表和建议。
5. 对某个药品继续追问。
6. 导出报告或复制到周会材料。

### 4. Agent 自动完成什么工作

- 识别用户问题属于库存、销售、区域、药品还是风险报告；
- 选择需要的表；
- 生成 SQL；
- 执行查询；
- 校验口径；
- 生成表格；
- 生成图表；
- 给出业务解释；
- 标注数据依据；
- 生成建议动作。

### 5. 产品最终交付什么结果

最重要的交付物不是一句回答，而是：

**可追溯的经营风险报告。**

包括：

- 风险排行榜；
- 异常指标；
- 药品明细；
- 区域明细；
- 图表；
- SQL 或数据依据；
- 分析口径；
- 建议动作；
- 可导出的周报/月报。

### 6. 哪个结果最值得用户付费

最值得付费的是：

**提前发现库存积压、近效期和滞销风险，并生成可直接用于经营会议的报告。**

因为它连接到真实损失：

- 库存占用资金；
- 药品过期损失；
- 销售策略滞后；
- 补货决策错误；
- 管理层追问时数据准备成本高。

### 7. 用户多久使用一次

- 每周固定生成经营周报；
- 每月生成经营复盘；
- 每天或隔天查看库存/近效期风险；
- 临时会议前自然语言追问。

如果产品只能临时问数，使用频率不稳定。加入周报和风险提醒后，才有持续价值。

### 8. 收费方式

第一版建议：

- 轻量 SaaS：按公司/月收费；
- 私有部署试点：按项目收费；
- 数据分析顾问式交付：按初始化 + 月费收费。

对第一批客户，最现实的是：

**初始化配置费 + 月度订阅。**

### 9. 第一版合理价格区间

面向中小客户：

- 试点版：人民币 999-2999 元/月；
- 带字段映射和报告模板配置：人民币 5000-15000 元初始化费 + 1999-4999 元/月；
- 私有化小项目：人民币 3-10 万元一次性试点。

不要一开始按 token 收费。业务用户关心的是报告和风险发现，不关心模型调用次数。

### 10. 为什么不会直接用 ChatGPT 替代

ChatGPT 可以解释数据，但不能稳定替代这个产品，原因是：

- ChatGPT 默认不知道企业数据库结构；
- 用户不想每次手工导出、脱敏、复制数据；
- ChatGPT 不会稳定复用企业指标口径；
- ChatGPT 不能定时生成周报；
- ChatGPT 不能持续跟踪同一套库存和销售规则；
- ChatGPT 输出不天然带 SQL、口径和数据追溯；
- ChatGPT 不知道企业内部字段映射和历史分析规则。

产品真正卖点不是“AI 会回答”，而是“接入企业经营数据后，持续发现风险并生成可追溯报告”。

## 9. 与 ChatGPT、Excel 和 BI 工具的差异

| 对比对象 | 用户已有能力 | 当前产品应提供的额外价值 |
|---|---|---|
| ChatGPT | 能解释、能写 SQL、能总结 | 直接连接业务数据，沉淀行业口径，定时生成报告，可追溯结果 |
| 手工 SQL | 精确、灵活 | 业务人员无需写 SQL，Agent 自动选表、生成查询、解释结果 |
| Excel | 灵活、普及 | 自动联表、自动口径、自动异常发现，减少手工透视和复制 |
| Power BI | 看板稳定、适合固定指标 | 临时自然语言追问、解释异常、生成经营建议 |
| 传统 BI 看板 | 标准化展示 | 主动发现风险，而不是只显示已有图表 |

最清晰的差异：

**BI 告诉你发生了什么；这个 Agent 应该告诉你哪里异常、为什么值得关注、下一步该查什么。**

## 10. 产品壁垒

### 真正可能形成壁垒的能力

| 壁垒 | 为什么有价值 |
|---|---|
| 行业数据模型 | 药品、批次、效期、库存、销售、区域、客户之间关系稳定，可复用 |
| 行业指标体系 | 库存销量比、可售月数、近效期风险、滞销风险、区域贡献等可沉淀 |
| 指标计算口径 | 口径正确性是业务信任基础，例如避免多表 JOIN 重复求和 |
| 异常检测规则 | 哪些库存风险、销售异常值得提醒，可持续优化 |
| 分析模板 | 周报、月报、药品分析、区域分析、库存风险报告可产品化 |
| 企业语义层 | 把用户字段映射为标准概念，降低每次接入成本 |
| 用户反馈数据 | 用户确认“这个异常有用/没用”，能改进规则 |
| Agent Eval 数据集 | 行业问题和标准答案越多，Agent 越稳定 |
| 工作流集成 | 自动推送周报和异常提醒会增强粘性 |

### 容易被复制的普通功能

- 输入框问数据库；
- LLM 生成 SQL；
- 简单柱状图；
- Markdown 报告；
- 普通 FastAPI 接口；
- 关键词 eval；
- 连接 MySQL。

这些不能当壁垒，只能当基础能力。

### 当前不值得投入的能力

- 大规模权限系统；
- 多模型智能路由；
- 自动训练私有模型；
- 通用 RAG 知识库；
- 通用 BI 图表设计器；
- 多行业模板市场；
- 复杂数据血缘平台。

这些只有在真实用户验证后才值得做。

## 11. 四阶段发展路线图

### 阶段一：完整 Demo

目标：能够稳定演示。

要开发的功能：

- `/api/task` 调用真实 Agent；
- 返回 answer、SQL、columns、rows、tool_steps；
- 简单 Web 页面；
- 示例问题按钮；
- 结果表格；
- 一到两种图表；
- SQL 和分析口径展示；
- 库存风险周报模板；
- eval 稳定通过。

要修复的问题：

- 空 query；
- eval 失败 exit 0；
- UTF-8 输出；
- 最小只读 SQL 限制；
- Top3/排序/单位输出不稳定。

完成标准：

- 本地一条命令启动后端；
- 打开页面即可演示 5 个固定问题；
- 每个问题都显示 SQL、表格、图表、结论；
- 库存风险问题连续运行 5 次结果一致；
- eval 至少 5/5 通过。

### 阶段二：用户试用 MVP

目标：让 3-10 个真实用户持续使用。

要开发的功能：

- 固定格式 CSV 导入或只读 MySQL 连接；
- 字段映射；
- 库存风险模板；
- 区域销售模板；
- 重点药品模板；
- 自动周报；
- 报告导出；
- 阈值配置；
- 用户反馈按钮：有用、无用、误报、需要补充。

用户验证方式：

- 找 3-10 个医药流通、药品销售、库存运营相关用户试用；
- 用他们真实脱敏数据跑一次周报；
- 观察他们是否会追问；
- 观察他们是否把报告发给同事或老板；
- 记录哪些建议被采纳。

需要收集的数据：

- 每周活跃次数；
- 每次分析的问题类型；
- 用户是否下载或转发报告；
- 用户认为有价值的异常数量；
- 误报数量；
- 报告节省的时间；
- 用户愿意支付的价格。

判断 MVP 是否成立的指标：

- 至少 5 个试用用户中有 3 个连续使用 4 周；
- 每个用户每周至少生成 1 次报告；
- 至少 50% 的报告被转发或用于会议；
- 用户能说出一个明确收益，例如提前发现积压、节省报表时间；
- 至少 1-2 个用户愿意付费试点。

### 阶段三：第一版付费产品

目标：获得第一批付费用户。

收费功能：

- 自动经营周报；
- 库存积压风险榜；
- 近效期风险预警；

产品包装：

不要叫“数据库问答 Agent”。建议包装为：

**医药库存与销售风险周报 Agent。**

主卖点：

- 业务人员不用写 SQL；

定价方式：

## 14. 最终结论

### 这个项目最适合发展成什么产品

最适合发展成 **制药行业库存与销售风险分析 Agent**，第一形态是“自动经营风险周报 + 自然语言追问”。

### 第一批用户是谁

第一批用户是中小制药企业、医药流通企业、药品代理商、连锁药房区域运营中的销售运营和库存运营负责人。

### 用户为什么愿意付费

因为它能减少库存积压和近效期损失，节省经营报表时间，帮助管理者更快发现销售和库存异常。用户付费买的不是聊天能力，而是持续经营风险发现和可直接用于会议的报告。

### 第一版产品提供什么

第一版提供：

- 数据接入；
- 字段映射；
- 库存风险分析；
- 近效期预警；
- 区域销售分析；
- 重点药品分析；
- 自动周报；
- 图表和数据依据；
- 自然语言追问。

### 当前代码应该保留什么

应该保留：

- DeepAgents 主 Agent 和数据库子 Agent 结构；
- MySQL 工具的基本意图；
- `sql/db.sql` 的制药样例数据模型；
- `prompt/prompts.yaml` 中关于多表聚合和库存风险的业务规则；
- `evals/db_agent_eval.py` 的验收问题集合。

### 当前代码应该优先改造什么

优先改造：

- API 和 Agent 的断裂；
- SQL 工具的任意执行问题；
- 工具返回纯字符串问题；
- eval 不稳定和失败不报错问题；
- 缺少图表和执行过程展示问题。

### 距离可以收费还有哪些关键步骤

距离收费还差 6 个关键步骤：

1. 完整 Demo 链路稳定可演示。
2. 能接入真实或脱敏用户数据。
3. 有库存风险和周报两个高价值模板。
4. 分析结果可追溯，用户能信任。
5. 真实用户连续使用 4 周。
6. 至少一个用户愿意为节省报表时间或发现库存风险付费。

最短路径不是做更大的 Agent，而是把当前 Agent 收窄成一个能稳定发现制药库存与销售风险的产品。
